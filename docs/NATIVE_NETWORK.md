# Native browser network client

`network.html` is a separate real Midnight.js client, with public Preview selected by default. `native.html` runs generated Compact circuits locally and does not generate proofs or send network transactions. The network page becomes available only when its actual bundle and generated assets are built. Loading it does not connect a wallet or send a request to the public network.

The [GitHub Pages network page](https://ibkr-bouncybot.github.io/Midnight-BallotLab/network.html) has commit-specific SDK/WASM loading evidence. A locally served copy also completed the real Lace browser-wallet election described below. Separately, the 0.6.1 hosted Node wallet acceptance workflow completed 17 confirmed transactions and 16 proof transactions, finalizing `[2,1,2,0,0]` at block 137 on its own fresh local development chain. [GITHUB_EXECUTION.md](GITHUB_EXECUTION.md) retains that Node run's precise address, transaction IDs, tested commit `fa94c3a19b4791441208ceae54a121faff2c588b` and run links. Wallet transactions from the hosted Pages origin remain untested.

Version 0.6.1 includes sealed 2–5 candidate-count handling, five fixed ciphertext lanes and an external scheduled local-devnet operator. | --- | --- |

These are the current [official Preview endpoints](https://docs.midnight.network/guides/networks-and-environments#environment-reference). ### Select Preview in Lace

1. Open the application in the **same browser where Lace is installed**, then open and unlock Lace. Enable its Midnight account; a Cardano-only connection does not work here.
2. In Lace 2.5.0, open **Settings → Network → Testnet → Midnight: Preview → Confirm**. This is the route used by the retained successful connection test. Selecting Preview on the application page does not switch the wallet's network.
3. Open **Settings → Midnight**, find **On this device**, select **Run in this app (WASM)** and choose **Save configuration**. Keep that mode selected for DUST generation and election transactions. This option and its offscreen worker route were checked in the signed Lace 2.5.0 and 2.5.1 packages. Do not choose **Custom proof server** or a delegated provider for this browser-only flow. The app cannot select or attest Lace’s private setting through DApp Connector API 4; see [the wallet-mode limitation](#wallet-mode-limitation).
4. Reload the application page after installing or enabling Lace, or click **Refresh wallet list**. Select Lace, enter a password for this application's local key storage, then click **Connect selected wallet** and approve Lace's permission request. Use at least 16 characters from three of these groups: uppercase, lowercase, numbers and symbols. Avoid sequences such as `1234` or `abcd`, and more than three identical characters in a row. The installed SDK checks these rules before requesting wallet access. This is not your wallet password or recovery phrase.

Connection progress and errors appear **directly below Connect**. If the panel says it is requesting a connection from Lace, open the extension to look for its permission request. This step does not request transaction approval.

If Midnight is missing from an existing Lace wallet, its account menu provides **Accounts → Add account → Midnight → Name → Next**, followed by authentication. Add the account to the existing wallet; do not recreate or re-import it just to change networks. This additional-account route was checked in the signed Lace 2.5.0 extension source, not exercised on the user's wallet.

**You do not need DUST to connect the wallet.** The retained Preview connection test used an unfunded wallet and made no prover request. Before deploying, voting or submitting another transaction:

1. Copy the Preview unshielded address (`mn_addr_preview…`) into the [Preview faucet](https://midnight-tmnight-preview.nethermind.dev/) and complete its CAPTCHA. The faucet supplies free test NIGHT and is rate limited.
2. After the test NIGHT arrives, open the **Midnight account** in Lace and select **Generate tDUST → Review transaction → Confirm**. Lace fills in your tDUST address automatically; you do not need to copy another wallet address into that field. Wait for the DUST balance to become usable. Receiving test NIGHT alone does not start DUST generation. See the [official funding guide](https://docs.midnight.network/guides/acquire-tokens).
3. Keep the application tab and Lace open while proving. The first proof can download public proving material; complex proofs can use substantial memory and take time. A failed or interrupted proof is not an accepted transaction. The browser-only path has no HTTP-prover fallback.

**Check public Preview services** sends read-only RPC and HTTP indexer queries after you click it. It checks the node's network name and a public block height; it does not connect a wallet, check DUST or generate a proof. Connecting a selected Preview wallet repeats those service checks before requesting wallet access. Wallet, network and service settings lock while connected so the form continues to describe the active session; disconnect before changing them.

### If a button is disabled or a check fails

- **No wallet appears:** check that Lace is enabled in this browser, has a Midnight account, and can access this site. Unlock it, reload the page and use **Refresh wallet list**. The application needs Midnight DApp Connector API 4; a Cardano-only wallet entry is insufficient.
- **Connect does not start:** select a discovered wallet, complete the storage-password field and read the panel directly below Connect. The page brings this panel into view and names the current connection stage: wallet permission, account, network, wallet proving settings, browser proving worker or browser storage. Failures use fixed messages without exposing raw wallet errors or private data. Invalid passwords produce visible feedback before the public-service preflight or wallet request. Check that Lace itself is on Midnight Preview, not only the application's network selector.
- **Public services pass but Lace does not connect:** the status below Connect identifies the current step: wallet permission, Midnight account access, matching network, wallet proving settings, browser-worker initialization or app storage. Failures use fixed guidance for that step without displaying wallet error payloads. A successful public-service check does not establish a wallet connection or a working proving worker. No transaction is submitted by Connect.
- **The app refuses a reported proof-server address:** select **Run in this app (WASM)** in Lace, save the setting and reconnect. The browser-only path refuses a reported HTTP(S) prover address, including localhost. A missing address permits this check to continue but is not proof that Lace is using on-device proving; its API also omits the address for a delegated TEE mode.
- **A browser proof cannot finish:** keep the tab open and check that the actual worker, WASM and public proving assets loaded. There is no server fallback. Do not resend a ballot after an uncertain wallet/submission result; resolve the existing attempt first.
- **The public-service check fails:** this check does not require Lace, DUST or a running prover. The displayed message identifies the node or indexer and distinguishes an HTTP response, an unreadable response, a transport failure or a timeout. A transport failure cannot reliably distinguish CORS, DNS, TLS, an offline device or browser/network restrictions. The messages use fixed safe text and a validated HTTP status; they do not display upstream error bodies. A service-check failure does not diagnose the wallet. Share only the displayed error text when asking for help, never a recovery phrase, private key or storage password.
- **All controls stay disabled:** read the page's loading/error message. The client keeps its controls disabled when its real SDK/WASM assets cannot load. Installing or funding a wallet does not fix an asset-loading failure.
- **Settings are locked after connection:** disconnect before changing the wallet or network. This keeps the visible form consistent with the active session.

### Wallet-mode limitation

DApp Connector API 4 exposes an optional, deprecated `proverServerUri` in `getConfiguration()` but no proving-mode field, attestation or app-supplied wallet prover callback. In the inspected signed Lace 2.5.0 and 2.5.1 packages, **both `in-process` and `tee-delegated` omit that URI**. Rechecking configuration before an operation can reject a reported external or loopback proof server; it cannot distinguish those two omitted-URI cases. A missing URI, user-selected option or successful proof must not be presented as cryptographic evidence of where the wallet processed its private data. Page CSP also does not constrain extension-origin network requests.

The normal Lace WASM setting routes both the wallet’s transaction proving service and its DApp circuit provider through an offscreen document and dedicated worker. Its reviewed ledger-8 public proving material uses version-directory `9`, matching the official [ledger 8.1.2 material version](https://github.com/midnightntwrk/midnight-ledger/blob/ledger-8.1.2/static/version); that number is not the ledger major version. `getProvingProvider(KeyMaterialProvider)` lets a DApp supply public contract keys for the wallet to prove; it does not expose wallet/DUST witnesses or install a DApp’s worker inside Lace. This application therefore proves its own contract work in its worker and leaves wallet/DUST work inside Lace.

Record actual application-worker proofs, the selected Lace mode, wallet/DUST proof behavior and accepted Preview transactions separately. The [current verification status](VERIFICATION_STATUS.md) distinguishes the completed browser election from its failed wallet-prover observation. The preceding HTTP-prover tests remain historical evidence; they are not proof of the new browser path. Never extract wallet secrets, patch the extension or silently use a remote prover to manufacture this result. See the [API specification](https://github.com/midnightntwrk/midnight-dapp-connector-api/blob/main/docs/api/_media/SPECIFICATION.md) and the [verified Lace package provenance](../evidence/2026-11-03/lace-wallet/package-verification.json).

## Run the flow

Use the published network page, or build the real native contract and network browser bundle and serve them over HTTPS or loopback. `keys/` and `zkir/` must be available under `native-contract/` alongside `network.html`; the bootstrap preserves GitHub repository subdirectory paths.

During an action, the current step and elapsed time appear beside its button and in Election activity. Contract proving happens before Lace's transaction approval request. The elapsed timer measures time spent in the whole action, not proof completion or a network deadline. Do not retry a pending action just because its button is disabled; wait for its outcome and check the public record if submission is uncertain.

1. **Connect.** Select Preview in Lace and your API-4 wallet in the app. Use **Check public Preview services**, enter a strong local storage password and connect. Funding is not required for connection. The app validates the password and public services before requesting wallet access; mainnet is rejected. Wallet account, network and reported prover configuration are rechecked before proving, balancing and submission. Connection settings stay locked until disconnect.
2. **Set up election.** Before a transaction, obtain usable test DUST and confirm Lace is still set to **Run in this app (WASM)**. Join with a trusted contract address and fingerprint, or create a test election with a future opening and closing schedule. Generate and register its trustee keys before enrollment, then save the election details and private trustee files. Registration is a separate proved `configureKeys` call; deployment does not prove private key setup.
3. **Vote.** Register each voter before the scheduled opening time. Submit **Open voting** during the voting window and wait for confirmation, then use the same registered voter key to choose and submit a ballot. **Ready to vote?** explains any unmet requirement. The contract checks membership, uniqueness and one-hot encryption; the client compares the indexed receipt with the ballot it constructed from the private inputs. Save the voter’s receipt.
4. **Reveal results.** Close voting after the real deadline, submit two registered trustee contributions and finalize with a supported pair. The contract uses the full frozen aggregate. Changing screens or reaching a countdown deadline does not advance the network clock or submit these transactions.
5. **Verify election.** Refresh or download the connected election record, compare a receipt against that record, or upload a saved record for local consistency checks without a wallet. Keep the full JSON/QR receipt: its QR carries the network, contract, configuration, ballot index and receipt hash, without a choice, randomness or transaction ID. A matching record does not independently authenticate chain inclusion.

In **02 / Set up election**, choose **Create a new election** to enter its name, choices and schedule, or **Join an election** to enter an existing contract address and trusted fingerprint. Choosing a view does not send a transaction. The administrator key tools remain available in either view. Once this session has created or joined a contract, the choice is locked; disconnect before selecting another election.

The blue **Your election, step by step** row switches between five separate screens: **01 Connect**, **02 Set up election**, **03 Vote**, **04 Reveal results** and **05 Verify election**. Only the selected screen is shown. Use its **Back / Next** controls or choose another blue stage button; **Election activity** remains available beside the current screen and stacks below it on narrow displays.

Switching screens preserves the current form values, private keys, receipt and uploaded-record result in this tab. It does not connect a wallet, join an election, refresh the indexer, send a transaction or advance the contract’s phase. You can open **Verify election** immediately to check a saved file without a wallet. Navigation is disabled while an action is running, keeping its progress visible. Refreshing or closing the browser remains different from changing screens and can discard the private session.

Existing links to headings and controls, such as `network.html#vote-heading` or `network.html#check-heading`, reveal the corresponding screen. A readiness or receipt link likewise opens its destination screen. These links do not bypass any action’s wallet, configuration, key or voting-window checks.

**Election activity** shows opening and closing dates from the last loaded contract record, with a countdown based on your device clock. It distinguishes scheduled voting, an opening transaction still needed, voting in progress, an elapsed voting window awaiting closing, a closed election awaiting the tally and finalized results. The time display does not send transactions or refresh the indexer automatically. Its last-updated time shows when the record was read; use **Refresh election record** to fetch the current phase. Reaching a deadline on your device is not evidence that a transaction has been accepted.

[Earlier navigation and timing evidence](../evidence/2026-11-06/network-stages/README.md) separates actual generated-ledger lifecycle checks from the browser’s navigation and unjoined-state checks. It records the preceding layout and is not a test of later screen-navigation changes.

The [earlier five-stage navigation check](../evidence/2026-11-06/five-stage-navigation/README.md) covers the **Verify election** shortcut on that build’s desktop, tablet and mobile layouts. The [new screen-navigation evidence](../evidence/2026-11-06/testnet-step-screens/README.md) records ten passing network-browser cases, including four viewport widths, preserved inputs/results, keyboard focus, direct links and browser history. It also retains the failing fragment-focus check and its successful correction, plus fresh native and provider checks. These checks generated no proof or transaction.

The **Save this election for later** card stays visible in **02 / Set up election**, in both Create and Join modes. After **Register trustee keys** is confirmed, use **Download election details** to save the network, contract address and fingerprint in a public JSON file. The fingerprint is created during key registration, so this download is unavailable immediately after deployment. It is also available after joining a configured election. The download rechecks the pinned configuration against the configured indexer; it does not independently authenticate blockchain history.

To return, select the same network and choose **Join an election → Load saved election details**. Loading the file fills the address and fingerprint without connecting, joining or submitting anything. Connect your wallet and click **Join election** to run the contract checks. The importer requires a JSON file up to 4 KiB with exactly the supported public fields; wrong-network, duplicate-field, malformed and private-key files are rejected without replacing the existing details. Share this public file with participants through a trusted channel.

## When voting is unavailable

**Ready to vote?** in stage 03 explains the current requirement and links to the relevant control. Connect the wallet, create or join the election, register trustee keys and register voters before the opening time. During the voting window, submit **Open voting** and wait for its confirmation. The contract does not execute an opening transaction merely because a countdown reaches zero. If another participant opened voting, use **Refresh voting status** to load that change.

The page checks the loaded voter key against the actual native election membership and spent-nullifier records before enabling choices. The checks run locally and disclose only readiness messages; they do not log the private key or derived identities. Load the key registered for this election rather than generating a replacement. Submission also requires an active choice, no unresolved vote attempt and a voting window that has not elapsed according to the device clock. The clock check is conservative UI guidance; the contract still validates the real transaction and its deadline. A stale record or incorrect device clock can require a refresh or clock correction.

A pending attempt remains locked until its outcome is resolved. It does not by itself prove that a transaction was submitted, and an absent receipt is not permission to submit again. None of these display checks advances the election, clears pending state or bypasses contract validation.

The [6 November readiness checks](../evidence/2026-11-06/voting-readiness/README.md) include actual generated-contract lifecycle and eligibility tests, real Chromium controls and a fresh, unfunded Lace 2.5.0 connection to Preview from a local application origin. ## Save and load trustee keys

After generating and registering the trustee shares, save **Download trustee 1 key**, **Download trustee 2 key** and **Download trustee 3 key** before leaving the setup session. Each private JSON file contains only one share, its trustee number and the public election identifiers. The filename includes the trustee number and an address prefix to help keep elections apart. Each download rechecks that the share matches the registered public key using the actual generated Midnight circuit helper; edited or regenerated shares that do not match are refused.

These files are **private and unencrypted**. Give each trustee only their own file, and keep them separate from public election details, receipts and election records. They are never included in public exports or logs. This file feature does not change the centralized demo key setup or its privacy limits.

A returning trustee joins the same election and chooses **Or load your saved trustee key** under **Reveal results**. The app validates the file’s network, address and fingerprint, refreshes the configured election, and uses the native public-key operation to check the share. Only then does it select the trustee and fill the hidden key field. Loading does not submit a contribution; the trustee still clicks **Submit trustee contribution** and approves any wallet request. A rejected file leaves the selected trustee and share unchanged. Imports accept only the exact supported JSON schema, valid UTF-8 and bounded nonzero scalar values, within 4 KiB.

The [file-backup checks](../evidence/2026-11-06/election-details/README.md) distinguish format tests, real generated-contract key matching and browser import/availability checks. They do not claim a newly executed wallet-connected backup/restore flow or accepted network transaction.

Transaction actions can request wallet approval and consume test-network DUST. Saving or loading a key file does not submit a transaction. Ending the local session clears its input fields and application references. It does not delete downloaded key files, revoke wallet permissions, erase encrypted SDK storage or guarantee erasure of JavaScript memory.

## Save and load administrator or voter keys

The administrator field starts empty and read-only. Choose **Generate administrator key** for a new election, **Use an existing key** to paste a saved key, or load its file. This explicit entry step helps prevent browser login autofill from being mistaken for an election key. **Generate administrator key** or **Generate voter key** creates a new key and shows it in its field. Use **Hide key** to mask it and **Show key** to reveal it again. For an existing administrator or registered voter, load the existing key instead of generating a replacement. The same administrator key tools are available when joining an existing election.

Use **Download key** beside the appropriate field. Administrator files are named `midnight-administrator-key.private.txt`. Voter files are numbered, for example `midnight-voter-key-000001.private.txt` and `midnight-voter-key-000002.private.txt`. The first download or cast assigns a number to that key; repeated downloads in the same session reuse it. Loading an original numbered key file restores its number and reserves the numeric counter so a new key does not immediately reuse it. A renamed file or pasted key gets a new number when first used unless already known in this session. This browser persists only the counter; the key-to-label mapping exists only in memory and is cleared on disconnect. If the counter cannot be saved, allocation uses a timestamp and a session counter. These are file labels, not registered voter IDs.

The receipt matches that label, for example `midnight-voter-000001-receipt.json`. Its filename is captured for the key used at casting, so selecting or generating another key does not rename the last receipt. A pending receipt keeps its original label for recovery in this session; if no label is available, a neutral receipt-ID filename is used. The number is not added to receipt JSON, QR data, network records, logs or public exports. The browser demo uses its selected demo voter number with the same receipt filename format.

These are **private, unencrypted text files**. Keep them separate from public receipts and election records; they contain the key only, with no vote, receipt, contract address or network. Anyone who obtains the applicable key can attempt actions authorized by that key. The application does not include these keys in public exports or logs.

To restore a key, choose its file under **Load a saved administrator key** or **Load a saved voter key**. It is loaded hidden; use **Show key** if needed. Import accepts a `.txt` file of at most 256 bytes containing one nonzero 64-character hexadecimal key, with optional surrounding whitespace. It validates UTF-8 and the key format before replacing the field. A rejected file leaves the current key unchanged. Format validation does not establish that the key belongs to the selected election; the actual contract checks its authority or membership when used. Loading a voter key does not register a voter or allow another vote after that voter has already voted.

**A key file is not a full election backup.** Also save the public election-details file or retain its network, contract address and trusted fingerprint. To return to an already configured election, connect a wallet to the same network, join using those details, then load the original administrator or voter key. These application keys are separate from the wallet that pays transaction fees. A complete restore followed by an accepted transaction in another browser has not been tested. Administrator/voter files do not restore trustee shares; use the separate private trustee files described above. None of these files restores a wallet, the dealer’s setup secrets, a pending receipt check, encrypted SDK storage or the rest of a browser session. Reloading between deployment and key configuration still cannot be recovered through Join; keep that setup session open until configuration finishes. The pending-vote limitation below also remains unchanged.

The [key-file and setup-control evidence](https://github.com/IBKR-BouncyBot/Midnight-BallotLab/blob/main/evidence/2026-11-04/private-key-backups/README.md) records eight passing browser scenarios, including actual private downloads and strict file rejection. A separate real Lace Preview connection checked mode selection and key clearing on disconnect. These controlled tests used disposable keys and an unfunded test wallet; they did not submit an election transaction or access the user's wallet.

If a ballot call has an uncertain result, the pending-ballot check retains only the locally expected public nullifier/receipt and checks the indexer without resubmitting. Further casts are blocked while it exists. This recovery state lasts only for the current client session, and a wallet rejection can also leave a pending record. Absence in an indexer is not evidence of non-submission. Check the transaction status through the wallet or a trusted network service before ending the session or making another attempt. Joining after reload currently requires an already configured election; resuming between deployment and key configuration needs additional deployment-state authentication and is not implemented. Keep the initial setup session open through key configuration.

## After voting and checking a receipt ID

After a ballot is found in the configured indexer's accepted record, the page shows its receipt ID and a **What happens next?** explanation. The sealed closing time is the earliest time voting can close. Results require a closing transaction, valid contributions from two trustees and a finalization transaction. The deadline alone does not publish totals; this page does not run the external operator. Once final totals are available, voters can review the public observation and compare their receipts.

**Paste receipt ID** accepts the 64-character hexadecimal ID from the receipt. It searches only the currently joined, configuration-pinned election, requires a unique accepted match and checks that ballot's native receipt digest, ciphertext and receipt-set membership. This is a lookup in the configured indexer's record. It does not establish ownership, authenticate the indexer, verify a transaction reference or independently prove chain inclusion. Keep the full receipt: unlike a bare ID, it also supplies the network, contract and configuration details to compare. Existing full-receipt validation remains available.

## Upload a downloaded network record

Open **05 / Verify election** directly with its blue stage button. **Upload a saved election record** accepts the JSON produced by **Download election record**, including files from earlier sessions. No wallet or connected election is needed, and completing the preceding screens is not required. The file is checked locally using the generated contract helpers and actual Midnight WASM. The result displays its network, contract address, fingerprint, recorded stage, ballot count and finalized totals. Choice names appear only when the optional election manifest matches its committed digest. Switching to another screen and back preserves this result; choosing another file clears the earlier result before checking it.

The importer requires valid UTF-8 JSON up to 8 MiB, bounded nesting and the exact `midnight-ballot-lab/native-indexed-observation/v1` schema. It rejects duplicate or extra fields, private data, invalid coordinates or subgroup points, inconsistent key/configuration relations, duplicate nullifiers, changed receipt commitments, incomplete aggregate sums and invalid finalized threshold equations. An unconfigured record cannot pass these checks; download it again after trustee-key registration. A failed upload clears any preceding upload result and preserves all connection/election settings.

The uploaded result is separate from **Election activity** and the live receipt lookups. Uploading never joins an election, changes the selected network, advances its phase, enables voting or sends a transaction. It validates consistency of the supplied public data, not the authenticity, freshness or completeness of the record. No ballot eligibility, ciphertext well-formedness, trustee contribution or chain-inclusion proof package is present. An internally consistent replacement record can still pass. The browser-demo snapshot schema remains separate and belongs in the browser demo's upload control.

## Evidence stages and privacy

The UI emits fixed stage labels only. It never logs raw SDK return objects, errors, transactions, private contexts or proof data. Confirmed operation records retain only a transaction ID, block height and explicit `configured-indexer` confirmation source. Receipt exports are an allowlist. Public observations reuse the public-ledger field projection with a distinct `native-indexed-observation/v1` schema and explicitly state that no proof package or independent chain verification is included.

The application’s proving worker receives private contract witnesses and uses official Midnight WASM locally. It has no HTTP proof fallback. Lace separately handles its wallet secrets and DUST witnesses; select its on-device mode. The application refuses a reported proof-server URI but cannot attest the omitted-URI mode through API 4. This distinction is described in [Wallet-mode limitation](#wallet-mode-limitation); do not label the whole wallet flow as independently verified on-device merely because the application worker returned a proof.

A prover return is not a submitted transaction. A wallet submission return is not confirmation. `callTx`/`deployContract` resolve after the configured indexer reports the outcome. That does not independently validate a canonical chain, honest deployment state or maintenance history. Verifier-key and configuration comparisons remain necessary but insufficient for an authenticated public election record.

The synthetic dealer knows the master secret and every share; this is not distributed key generation. Two colluding trustees can decrypt individual ciphertexts outside this contract. Eligibility administration, device trust, coercion resistance and cast-as-intended assurance remain outside this prototype.
