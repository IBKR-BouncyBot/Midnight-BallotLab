# Native development network client

`network.html` is a separate real Midnight.js client. `native.html` runs generated Compact circuits locally and does not generate proofs or send network transactions. The network page becomes available only when its actual bundle and generated assets are built. Loading the page does not connect a wallet.

The [GitHub Pages network page](https://ibkr-bouncybot.github.io/Midnight-BallotLab/network.html) has commit-specific SDK/WASM loading evidence. A locally served copy also completed the real Lace browser-wallet election described below. Separately, the 0.6.1 hosted Node wallet acceptance workflow completed 17 confirmed transactions and 16 proof transactions, finalizing `[2,1,2,0,0]` at block 137 on its own fresh local development chain. [GITHUB_EXECUTION.md](GITHUB_EXECUTION.md) retains that Node run's precise address, transaction IDs, tested commit `fa94c3a19b4791441208ceae54a121faff2c588b` and run links. Wallet transactions from the hosted Pages origin remain untested.

Version 0.6.1 includes sealed 2–5 candidate-count handling, five fixed ciphertext lanes and an external scheduled local-devnet operator. Its successful network run waited for actual indexed time after the sealed closing deadline, then submitted closing, trustee contributions 1 + 3 and finalization. The preceding 0.6.0 failure at its fifth ballot remains separately retained; it is not relabeled as passing. The local browser's scheduled preview and public JSON verifier are separate features; neither submits a network transaction or authenticates a network record.

## Wallet compatibility

**Midnight-enabled Lace 2.5.0, exposing DApp Connector API 4.0.1, completed a full election through this application's real browser UI on the local `undeployed` network.** The [retained browser report](https://github.com/IBKR-BouncyBot/Midnight-BallotLab/blob/main/evidence/2026-11-03/lace-wallet/attempt-2/browser-election.json) records wallet approval, proving, submission and configured-indexer acceptance. The official [Midnight browser guide](https://docs.midnight.network/guides/browser-dapp) describes Lace 2.4.3; the version tested here is [Lace 2.5.0](https://chromewebstore.google.com/detail/lace/gafhhkghbfjjkeiendhlofajokpaflmk), whose [official announcement](https://www.lace.io/blog/lace-2-5-more-control-smoother-transactions) describes its Midnight features. [Package verification](https://github.com/IBKR-BouncyBot/Midnight-BallotLab/blob/main/evidence/2026-11-03/lace-wallet/package-verification.json) retains the extension digest and verified developer/Web Store signatures.

The wallet picker discovers API-4 entries under `window.midnight`, including their name and `rdns`; it does not certify a wallet publisher. Other wallets are conditional candidates only if they implement the required API and satisfy these checks. A Cardano-only wallet or CIP-30 connection under `window.cardano` is not supported. Having ADA or Cardano NIGHT does not provide the Midnight connector used here.

- The wallet must connect to the selected `undeployed`, `preview` or `preprod` network and expose shielded/unshielded addresses, wallet-delegated proving, transaction balancing and submission. Mainnet is rejected.
- The wallet must report a loopback HTTP(S) `proverServerUri` in `getConfiguration()`. API 4 makes this field optional and deprecated, so a wallet that omits it currently fails closed even if it otherwise implements API 4. The application uses `getProvingProvider()` for proving. See the official [DApp Connector release notes](https://github.com/midnightntwrk/midnight-dapp-connector-api/releases). A reported URL does not attest to the wallet or prover process.
- A working indexer for the selected network, a running local prover and usable development-network DUST are separate requirements. Installing an extension does not supply these services.

The [installed-provider boundary tests](../evidence/2026-11-03/wallet-readiness/provider-boundaries.log) passed three cases, and [Chromium loading checks](../evidence/2026-11-03/wallet-readiness/network-browser.json) passed four no-wallet cases. Those tests establish loading/rejection behavior only. The real Lace run below adds browser-wallet transaction evidence; the Node-wallet development-chain runs remain separate evidence. No other browser wallet has been tested.

## Dependencies and APIs inspected

The supplied compiler/runtime/SDK pins remain the supported ledger-8 combination in the official [compatibility matrix](https://docs.midnight.network/relnotes/support-matrix), checked on 3 November 2026: Compact 0.31.1, compact-runtime 0.16.0, onchain-runtime-v3 3.0.0 and Midnight.js 4.1.1. Do not substitute the newer ledger-9 compiler/runtime while using this SDK/network combination.

`contracts/native/browser-providers.mjs` uses the installed Midnight.js 4.1.1 implementations for wallet-delegated proving, fetched ZK assets, indexer data and encrypted private-state storage. Its wallet bridge uses DApp Connector API 4.0.1 transaction serialization. Export names and signatures were checked against the installed package declarations and the tagged SDK source. The [official browser guide](https://docs.midnight.network/guides/browser-dapp) describes this provider split.

The browser build includes the real `events`, `assert`, `buffer` and `process/browser` packages where SDK dependencies require their browser implementations. An actual Chromium load exposed an unbound `process` reference in `util`; the network build now injects the installed browser `process` and `Buffer` implementations. These are platform compatibility dependencies, not replacements for the generated contract or Midnight WASM. The indexer provider receives the browser's native `WebSocket` constructor explicitly.

For plain-HTTP/WS local indexers, use `localhost` or `127.0.0.1`. Chromium rejected IPv6 literal CSP host sources in the browser acceptance run, so those directives were removed and insecure IPv6 indexer URLs now fail configuration validation. The wallet's independently inspected `::1` prover and same-origin frontend assets are unaffected.

## Run the flow

1. Build the real native contract and network browser bundle. Serve the frontend over HTTPS or loopback. `keys/` and `zkir/` must be available under `native-contract/` alongside `network.html`; the bootstrap preserves GitHub repository subdirectory paths.
2. Open the page in a browser with a DApp Connector API 4 wallet. Select that wallet, an explicit development network and its matching HTTP/WebSocket indexer endpoints. No network is chosen by default. Mainnet is rejected by the application.
3. Configure a trusted local prover in the wallet and supply a strong local storage password. The page validates the password before requesting wallet access. Wallet account, network and reported prover configuration are rechecked before proving, balancing and submission.
4. Join using a separately authenticated contract address and expected configuration digest, or deploy a new synthetic test election with a future opening/closing schedule. New elections require a separate, proved `configureKeys` call before enrollment. A deployment transaction does not prove private key setup.
5. Enroll the synthetic voter credential before opening, open after the real opening time, and cast with that same secret. The contract enforces membership, uniqueness and one-hot ciphertext construction. The client compares the indexed receipt against the ballot it constructed locally from the actual private inputs.
6. Close after the real deadline, submit two registered trustee contributions and finalize using one supported pair. The contract operates on the full frozen aggregate. The page does not advance the network clock.
7. Keep public JSON/QR receipts and use the public checks. A QR carries the network, contract, configuration, ballot index and receipt hash, without a choice or encryption randomness. It excludes the transaction ID; checking its ciphertext binding does not independently authenticate chain inclusion.

All network operations can request wallet approval and consume test-network DUST. Generated synthetic secrets remain in this browser session. The page does not supply private credential backups; retain operational credentials securely before leaving. Ending the local session clears its input fields and application references. It does not revoke wallet permissions, erase encrypted SDK storage or guarantee erasure of JavaScript memory.

If a ballot call has an uncertain result, the pending-ballot check retains only the locally expected public nullifier/receipt and checks the indexer without resubmitting. Further casts are blocked while it exists. This recovery state lasts only for the current client session, and a wallet rejection can also leave a pending record. Absence in an indexer is not evidence of non-submission. Check the transaction status through the wallet or a trusted network service before ending the session or making another attempt. Joining after reload currently requires an already configured election; resuming between deployment and key configuration needs additional deployment-state authentication and is not implemented. Keep the initial setup session open through key configuration.

## Evidence stages and privacy

The UI emits fixed stage labels only. It never logs raw SDK return objects, errors, transactions, private contexts or proof data. Confirmed operation records retain only a transaction ID, block height and explicit `configured-indexer` confirmation source. Receipt exports are an allowlist. Public observations reuse the public-ledger field projection with a distinct `native-indexed-observation/v1` schema and explicitly state that no proof package or independent chain verification is included.

The proving provider receives private witnesses. This prototype requires the wallet to report a loopback `proverServerUri`; that optional API-4 field is deprecated, so wallets that omit it currently fail closed. The page uses `getProvingProvider`, not a custom HTTP proof implementation. A reported loopback URL is not attestation of wallet integrity or of the process listening on that port.

A prover return is not a submitted transaction. A wallet submission return is not confirmation. `callTx`/`deployContract` resolve after the configured indexer reports the outcome. That does not independently validate a canonical chain, honest deployment state or maintenance history. Verifier-key and configuration comparisons remain necessary but insufficient for an authenticated public election record.

The synthetic dealer knows the master secret and every share; this is not distributed key generation. Two colluding trustees can decrypt individual ciphertexts outside this contract. Eligibility administration, device trust, coercion resistance and cast-as-intended assurance remain outside this prototype.

## External scheduled development operator

`contracts/devnet/scheduled-operator.mjs` is invoked by the isolated acceptance runner. It reads the sealed closing deadline, waits for both actual wall-clock and indexed block time, then closes, supplies two externally provided synthetic trustee shares and finalizes through the real SDK providers. Each step requires configured-indexer acceptance. It does not bypass deadline/share constraints, change node time or make the chain execute itself. A running operator, wallet, prover and indexer are required. Hosting the frontend on Pages does not run this service. See [the operator instructions](../contracts/devnet/README.md).

A readiness result or a locally generated proof is not an accepted transaction. The runner requires `SucceedEntirely` from the configured indexer for every counted transaction and compares native receipts and final totals. This establishes accepted local development transactions under that confirmation source, without authenticating the indexer or independently verifying canonical chain inclusion. The evidence contains the contract address, configuration digest, public transaction identifiers, source hashes and exact dependency versions.

The separate local Lace run above establishes actual browser-wallet connection and application transactions. The Node runner alone does not establish browser-wallet behavior. Hosted-origin wallet transactions, Preview/Preprod access and public-network transactions remain untested. Preprod service access can require a user-supplied Blockfrost project token; do not invent one or publish a private credential. No wallet seed belongs in this repository, a frontend bundle or CI.

The application deliberately does not offer a public authenticated-proof-verification claim. A future independent verifier must authenticate deployment/initial state, circuit and verifier-key provenance, key configuration, accepted chain state and maintenance policy. The current public export alone cannot establish these facts or certify an election.
