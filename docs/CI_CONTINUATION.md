## Publication gates and evidence

The Pages workflow always compiles and tests the generated native election, runs the native example, builds the static site, bundles the real native runtime/WASM and network client, and runs the actual Chromium acceptance scripts. Native output is required on every publishing run. A compiler, runtime, test, bundle, browser or packaging failure prevents deployment. The native manifest is checked, never modified by CI.

The browser-WASM proof gate now requires two separately reported results: **eight standalone proofs across all seven circuit types**, and **one genuine `configureKeys` Ledger transaction proved through the production `proveTx` provider**. The transaction case is constructed by the official SDK from actual generated state; its strict v2 report must record ordered `check`/`prove` callbacks, a present binding override, and only public proof hashes, sizes and timings. It runs before the mismatched-circuit negative check stops the worker. The earlier [successful v1 CI report](../evidence/2026-11-06/browser-wasm/github-42271382645/README.md) covered standalone proofs only; it does not establish a pass for this added transaction case. A fresh completed v2 report is required before claiming that result.

Both workflows run the Ledger failure-diagnostic regression only after native compilation and retain its separate log. The browser proof gate has a 50-minute overall deadline within a 55-minute step and a 90-minute job; the worker retains its 15-minute limit per request. All witnesses and unproven transactions remain in browser memory. The test has no wallet, HTTP proof provider or network submission, so even a successful transaction-proof case does not establish Lace wallet/DUST proving, accepted transactions, independent proof verification or hosted-origin behavior.

The build uses Bash's GitHub Actions failure handling (`-e -o pipefail`), so a command piped to `tee` cannot succeed merely because log writing succeeds. Evidence artifacts retain tool versions, the installed dependency tree, the reviewed lockfile, compiler/test/build logs, the native build manifest and the public synthetic-election snapshot for 30 days. They deliberately exclude private contexts, proof witness data, wallet data and generated compiler directories. Logs come only from the public compiler/build tasks and synthetic test fixtures. They are not suitable for logging real voter input.

The current **Midnight contract compatibility** workflow compiles/tests the native election, runs the generated example and both real browser gates, and requires browser-WASM proofs. It starts no HTTP prover. The standalone proof-server 8.1.3 smoke and isolated wallet-graph checks are retained in the separate historical ledger-8 devnet workflow, behind its explicit compatibility preflight. No old-runtime check is silently treated as a ledger-9 pass. Full compilation still generates real circuit/key assets; key generation alone is not proof generation.

Passing the build/browser stages establishes generated-contract execution and real local Chromium execution. The native browser gate covers configurable elections, trustee pairs, QR decoding, public exports/imports, receipts, root/subdirectory hosting and failure handling. Source coverage is not a passing result; retain each actual run's report. Network browser tests cover real SDK initialization and unavailable-wallet/error paths. The separate successful local proof stage establishes circuit proof generation. These stages do not establish wallet integration success, accepted transactions, independent proof verification, authenticated election-state verification or successful Pages deployment. Those need their own recorded outcomes, including a check at the eventual Pages project URL.

Fresh local execution and the successful hosted compatibility run on 3 November 2026 each produced eight proof responses across all seven circuit types and passed both negative checks. Their evidence is retained separately. The proof client uses the official provider's fixed retry behavior; version 4.1.1 offers no public option to disable its three retries on HTTP 500/503.

## Deployment boundaries

Pull requests and manual runs on nonrelease branches cannot deploy. Only a successful build on `main` or `master` reaches the `github-pages` environment with `pages: write` and `id-token: write`. Environment protections may require repository-owner action. Pages hosts the frontend only; it does not deploy a Midnight contract or supply a prover, indexer or node. ChatGPT Sites is not involved.

GitHub Pages ignores the build's `_headers` file. Page metadata can enforce a content security policy, but this does not set server-only response headers. Check the deployed response and browser behavior separately.
