# Manual Lace Preview acceptance

`lace-preview-acceptance.yml` is a separate, manual workflow for the trusted `main` branch of `IBKR-BouncyBot/Midnight-BallotLab`. It is not a pull-request gate or a Pages deployment. Its intended result is a complete nine-operation election using the actual application, a disposable official Lace wallet and public Preview. Source checks are not proof that this workflow has completed successfully; inspect the exact run and its final public report.

Creating the wallet requires explicit approval of Lace 2.5.1 onboarding, including its [Terms and Conditions](https://www.lace.io/iohktermsandconditions.pdf) and [Privacy Policy](https://www.lace.io/lace-privacy-policy.pdf). The dispatch input defaults to false. Set it to true only after that approval is given. Acquisition pins the signed official extension version and archive/manifest hashes; version drift fails instead of silently changing the wallet.

The workflow compiles the real contract and builds its browser/WASM proving files, then starts one headed Chromium process under Xvfb. The same wallet profile remains alive throughout funding and the election. Its private profile and private diagnostic output stay under `RUNNER_TEMP`; neither is an artifact. Application proofs must use the actual browser worker, and the runner selects Lace's on-device WASM mode for wallet/DUST work. There is no HTTP-prover fallback. API 4 alone cannot attest the selected wallet proving mode.

Before creating any wallet, browser setup installs full Chromium with `--no-shell` and tries the existing runner environment. A separate check requires `xvfb-run` and `xauth`, launches real headed Chromium, loads only `about:blank`, and closes it. Playwright's host-dependency validation stays enabled. Only a failed check triggers the official dependency installer, with bounded APT network timeouts/retries and a total repair limit, followed by the same mandatory real launch. Finite initial/repair reports are retained separately as `lace-browser-environment-RUN_ID`. The [attempt-6 initial report](../evidence/2026-11-06/lace-preview/attempt-6/environment-initial.json) passed: full Chromium installed in six seconds and the real headed check completed in two seconds. Both repair steps were skipped, so the fallback path remains unexercised. This environment gate loaded no extension or wallet and is separate from the attempt's later acceptance result.

## Funding handoff

1. Start a fresh manual run after the source/acquisition review and onboarding approval. The workflow rejects rerun attempts; it does not automatically repeat a transaction or funding operation.
2. Wait for artifact `lace-preview-funding-RUN_ID`. It contains only the public funding request and signed-extension acquisition report. The browser continues running while this artifact is uploaded.
3. Verify the artifact's repository, exact source commit and run ID before using it. The strict request binds those identifiers, a nonce, `networkId: preview`, the canonical unshielded Preview address and a maximum of `5000000000` atomic test units. It contains no wallet secret. The bridge validates the address with the installed official Midnight address codec.
4. Fund that exact disposable wallet once through a separately authorized test-fund transfer. Funding is not performed by this workflow, and sponsor SDK proofs are not evidence of browser proving. Never use mainnet or real funds.
5. Let the same process continue. It waits for a balance, uses the wallet's actual Generate tDUST controls, and performs the election through the application and wallet UI. A timeout or uncertain operation is a failure to investigate, not permission to retry.

The funding request must appear within 20 minutes of startup. Funding can wait up to 60 minutes; each wallet synchronization/DUST wait has a 45-minute limit. Each application operation has a 20-minute limit, the runner has a 180-minute overall limit, and the job has a 210-minute limit. The election opens 15 minutes after setup and closes 25 minutes later, using its sealed deadlines. Neither a timer nor the supervisor can open, close or finalize it without the real actions.

## Evidence and cleanup

The final artifact, `lace-preview-evidence-RUN_ID`, explicitly allows only the acquisition report, funding request, browser report, public transaction journal, and optional public receipt/indexed observation. No directory wildcard, wallet profile, private log, screenshot, trace or video is uploaded. The journal records an operation before its first initiating click and preserves uncertain outcomes.

While waiting, the supervisor reads only the atomically written public browser report. It prints changes in a fixed set of stage names, overall/DUST statuses and operation ordinals/statuses/phases. It validates the run, commit and Preview context, and never prints addresses, URLs, arbitrary report fields or the private runner log. Missing initial reports produce no line; invalid progress produces a fixed `unavailable` marker without interrupting a possibly funded operation. This progress display does not replace the strict terminal acceptance check.

Success requires process exit zero, a matching run/commit report with `status: passed`, and exactly nine operations marked `indexer-accepted`. This is configured-indexer confirmation, not independently authenticated consensus. The report must continue to distinguish browser proofs from funding, preserve zero retries, and leave hosted-origin testing and independent chain verification false. The app is served locally on the CI runner; the GitHub Pages origin is not requested.

Cleanup signals only the verified task-owned process group. The runner closes its browser and removes its private profile; the ephemeral CI environment supplies the final isolation boundary. A failed run retains any available public partial report without converting it into success.

## Separate fundless wallet-prover diagnostic

[`lace-prover-diagnostic.yml`](../.github/workflows/lace-prover-diagnostic.yml) is a separate manual trusted-main workflow. It requires the same explicit Lace 2.5.1 onboarding approval and verified official extension. It does not fund the wallet, query its balances, register DUST, approve signing, submit a transaction or run the nine-operation election. The [first run](../evidence/2026-11-06/lace-preview/fundless-diagnostic-1/README.md) failed during application connection before its proof fixture. The [second run, 42311886874](../evidence/2026-11-06/lace-preview/fundless-diagnostic-2/README.md), connected the direct fixture through normal genuine-wallet authorization. Its constraint check completed and Lace returned a 2,933-byte `openVoting` contract proof; the preparation/check/proving interval was 17,319 ms. No independent proof verification was performed. The overall result remains **failed**: the passive observer reported zero matching targets and no exact wallet proving-WASM resource. The narrower fixture result does not diagnose the earlier main-application connection timeout or establish wallet/DUST proof execution.

The CI-only fixture requests a genuine `openVoting` constraint check and contract proof through Lace using fresh synthetic inputs in browser memory. A passive observer is armed before that request and accepts only the signed wallet's exact prover WASM resource, with pinned path, byte length and SHA-256. It does not evaluate extension code, pause execution, inspect request payloads or claim complete extension-network coverage. A loaded resource and this contract proof would not count as a wallet/DUST fee-proof test or API attestation of all wallet processing.

A passed result requires both the actual proof and the exact successful resource observation. A failed observation retains the proof summary, if any, without changing the overall failure. The runner has a 30-minute total limit and a 20-minute proof wait; the workflow is bounded to 45 minutes. There is no automatic retry. Only the validated `prover-diagnostic-report.json` and acquisition report can enter its diagnostic artifact; the separate browser-environment artifact contains finite setup checks. Private browser output and the temporary profile are never uploaded. Normal cleanup closes the browser and removes the profile; forced termination is additionally confined to the ephemeral runner.

## Executed attempts

The [first isolated run](../evidence/2026-11-06/lace-preview/attempt-1/README.md) created a genuine Lace 2.5.1 wallet, then timed out while selecting network/prover settings. It produced no funding request and executed no application transaction. The retained report is failure evidence, not a completed browser-wallet election.

The [second run](../evidence/2026-11-06/lace-preview/attempt-2/README.md) identified the timeout after Save in the proving settings: the sheet remained open. It also stopped before funding or application connection. Its control-level diagnostics do not establish a saved proving mode.

The [third run, 42285202601](../evidence/2026-11-06/lace-preview/attempt-3/README.md), verified the Midnight-only account selection and saved on-device WASM setting, connected genuine Lace 2.5.1/API 4.1.0-canary to the local application, and produced a public funding request. The separate sponsor transferred 5,000 test NIGHT successfully, but the browser did not record observing that funding. The run was deliberately cancelled at `waiting-for-authorized-test-funding`; its final public report records `runner-interrupted`, zero application operations, and no DUST generation. Do not retry the funding transfer or treat sponsor acceptance as browser-wallet acceptance.

The [public configuration policy review](../evidence/2026-11-06/lace-preview/policy-review/README.md) covers a narrow allowance for Lace's normal vendor service-configuration request and a wallet-endpoint check before funding. These source checks do not prove that wallet synchronization or a new complete election has succeeded. The [read-only CI service diagnostic](../evidence/2026-11-06/lace-preview/service-diagnostic/README.md) observed HTTP 410 from the signed build's default indexer URL and HTTP 200 from the official Preview endpoint. Those host-specific results do not establish which endpoint the dynamically configured wallet used or explain its wait by themselves.

[Inspection of the signed wallet source](../evidence/2026-11-06/lace-preview/normal-configuration-source-review.json) found that received configuration is first stored as `next`; the active `loaded` configuration changes on a background reload, and the normal automatic reload waits for all extension views to close. The current runner closes ordinary extension views and observes the old background worker close, then performs one normal browser-context restart using the same temporary profile before creating a wallet. It reinstalls the same request policies and waits for normal onboarding. Visible current-service labels before Save and exact wallet API endpoint agreement afterward remain required. The ninth run subsequently passed that normal restart, visible-service and API-agreement sequence. This configuration result remains separate from its final wallet-proof resource observation failure.

The [fourth run](../evidence/2026-11-06/lace-preview/attempt-4/README.md) observed Lace's genuine public configuration response, then stopped before funding at the settings-usability check. Its controls were enabled, but the test expected a literal `aria-disabled="false"`; the signed wallet's React Native Web code omits that attribute when false. The corrected check accepts an enabled control with no disabled attribute and still requires closing and reopening settings to verify the saved WASM selection. This is a test correction, not a completed wallet-proof result.

The [fifth run's public report](../evidence/2026-11-06/lace-preview/attempt-5/browser-report.json) records a bounded timeout at `verify-persisted-wallet-on-device-selection`, before application connection or funding. No saved proving-mode, DUST or application transaction success is claimed. The subsequent runner change checks stable selection and permits one normal keyboard Save action before requiring closure and a fresh reopen check; it has not yet established successful wallet acceptance.

The [sixth run](../evidence/2026-11-06/lace-preview/attempt-6/README.md) passed the UI persistence check for on-device WASM and connected genuine Lace to the application. It then stopped at `wallet-current-vendor-services-required`: the received vendor configuration named the new services, but the wallet API still reported the retired endpoints. No funding request, DUST registration or application operation followed. The service guard remained enforced; a successful configuration response alone was not accepted as proof of active wallet configuration.

The [seventh run](../evidence/2026-11-06/lace-preview/attempt-7/README.md) advanced past the old-worker-close check and failed while reopening the wallet after normal configuration activation, before creating a wallet or requesting funds. Its separate headed-browser environment check passed. The following run tested bounded ordinary pre-creation navigation and replacement-worker/onboarding waits; it did not retry a wallet action, funding transfer or transaction.

The [eighth run](../evidence/2026-11-06/lace-preview/attempt-8/README.md) observed the old worker close but no replacement. All three bounded normal extension-page navigation attempts returned `ERR_BLOCKED_BY_CLIENT`, before wallet creation or funding. Its initial browser-environment check passed. This establishes blocked navigation in that run, not its precise internal cause. The ninth run subsequently used the single normal same-profile restart described above and passed configuration activation; the original blocked-navigation result is unchanged.

Its on-device mode selection, usable DUST and accepted transactions are not a replacement for that missing evidence. The original failed report is preserved.
